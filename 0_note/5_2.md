我比如当前在master分支，然后我add一个到暂存区，然后可以切换到另一个分支，然后commit近另一个分支

## 分支切换问题

### 前置约定

主分支：`master`（稳定、可上线）
开发分支：`dev`（日常开发）
功能分支：`feat/xxx`（做单个新功能）

> 原则：**尽量不带未提交的改动来回切分支**，这是工作里最基本的习惯。

---

## 例子1：正在dev写一半，突然要去master改一个紧急bug（最常用）

场景：你在dev写代码，改了一半，不能commit（还没写完），要切master修bug
✅ 标准做法：`stash` 暂存改动

```bash
# 1. 把当前所有改动打包收起来，工作区变干净
git stash
# 2. 切主分支修bug
git switch master
# 修改bug，add + commit
git add .
git commit -m "fix: 紧急修复xx问题"
# 3. 切回dev，把刚才存的改动拿回来继续写
git switch dev
git stash pop
```

👉 好处：分支之间互不干扰，不会乱串文件。

## 例子2：在feat分支写完功能，合并到dev

场景：单独开分支做功能，做完合并进dev测试

```bash
# 1. 切到功能分支写完，提交
git switch feat/demo
git add .
git commit -m "feat: 新增xxx功能"
# 2. 切到dev，合并这个功能分支
git switch dev
git merge feat/demo
# 合并完，测试没问题，可以删掉功能分支
git branch -d feat/demo
```

## 例子3：不小心在master写了代码，想挪到dev（对应你刚才好奇的场景）

场景：手滑，在master改了代码还没commit，不该放master
两种方案：
方案A（改动还没commit，推荐stash）

```bash
git stash
git switch dev
git stash pop
# 现在改动在dev，在这里commit
```

方案B（已经commit在master了，想把这个提交挪去dev，master删掉这条）

```bash
# 先切dev，把提交拿过来
git switch dev
git cherry-pick 提交hash
# master回退掉这条错误提交
git switch master
git reset --hard 上一个hash
```

## 例子4：合并的时候遇到冲突（最头疼）

dev合并feat分支，同一个文件两边都改了，git自动合并失败，报冲突

```bash
git switch dev
git merge feat/demo
# 提示冲突，打开文件，找到 <<<<<<< 标记，手动选保留什么内容
# 改完保存
git add .
git commit -m "merge: 合并feat，解决冲突"
```

---

### 一句话总结工作习惯

1. 没写完的代码不要到处带着切分支，**用stash收起来**
2. 一个功能一个分支，写完commit，再合并
3. 不要利用“带着暂存区切分支提交”这个玩法，容易混乱，工作几乎没人这么写
